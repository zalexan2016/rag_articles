# Документ требований

## Введение

REST API для RAG-системы на базе FastAPI. Предоставляет HTTP-эндпоинт для отправки вопросов и получения ответов с источниками и изображениями. Аутентификация через API-ключ. Запуск сервера интегрирован в существующий CLI через флаг `--api` в `main.py`. API и Telegram-бот могут работать параллельно как отдельные процессы. Архитектура поддерживает добавление новых маршрутов в будущем.

## Глоссарий

- **API_Server**: Асинхронный HTTP-сервер на базе FastAPI, обслуживающий REST API RAG-системы
- **Client**: Внешний потребитель API, отправляющий HTTP-запросы к API_Server
- **RAGChain**: Существующий класс, выполняющий поиск по векторной базе и генерацию ответа через LLM
- **API_Key**: Секретный токен из переменной окружения API_KEY, используемый для аутентификации запросов
- **Query_Endpoint**: Эндпоинт GET /query, принимающий вопрос через query-параметр и возвращающий ответ RAG-системы
- **PID_File**: Файл, хранящий идентификатор процесса (api.pid или bot.pid) для управления жизненным циклом сервисов
- **Router**: FastAPI APIRouter для группировки и организации маршрутов

## Требования

### Требование 1: Эндпоинт запросов

**User Story:** Как Client, я хочу отправить вопрос в RAG-систему по HTTP, чтобы получить ответ с источниками и релевантными изображениями.

#### Критерии приёмки

1. WHEN GET-запрос с непустым query-параметром `question` поступает на `/query`, THE API_Server SHALL вызвать RAGChain.process с переданным вопросом и вернуть JSON-ответ со статусом 200, содержащий `{"answer": "...", "sources": [...], "image_paths": [...]}`
2. WHEN query-параметр `question` является пустой строкой или содержит только пробельные символы, THE API_Server SHALL вернуть JSON-ответ об ошибке со статусом 422 и описательным сообщением валидации
3. WHEN query-параметр `question` отсутствует в запросе, THE API_Server SHALL вернуть JSON-ответ об ошибке со статусом 422
4. THE API_Server SHALL использовать Pydantic-модель для валидации query-параметров (QueryParams с полем `question: str` и ограничением min_length)
5. THE API_Server SHALL использовать Pydantic-модель для сериализации ответа (QueryResponse с полями `answer: str`, `sources: list[str]`, `image_paths: list[str]`)

### Требование 2: Аутентификация

**User Story:** Как системный администратор, я хочу аутентифицировать API-запросы через API-ключ, чтобы только авторизованные клиенты имели доступ к RAG-системе.

#### Критерии приёмки

1. WHEN запрос к `/query` содержит валидный API_Key в заголовке `Authorization` по схеме Bearer, THE API_Server SHALL обработать запрос в штатном режиме
2. WHEN запрос к `/query` не содержит заголовок `Authorization`, THE API_Server SHALL вернуть JSON-ответ об ошибке со статусом 401 и сообщением об отсутствии учётных данных
3. WHEN запрос к `/query` содержит невалидный API_Key в заголовке `Authorization`, THE API_Server SHALL вернуть JSON-ответ об ошибке со статусом 403 и сообщением о невалидных учётных данных
4. WHILE переменная окружения API_KEY пуста или не задана, THE API_Server SHALL отклонять все запросы к `/query` со статусом 503 и сообщением о том, что сервис не сконфигурирован

### Требование 3: Запуск сервера через CLI

**User Story:** Как разработчик, я хочу запускать API-сервер флагом `--api` в `main.py`, чтобы он интегрировался в существующий CLI-процесс.

#### Критерии приёмки

1. WHEN флаг `--api` передан в `main.py`, THE API_Server SHALL запустить асинхронный HTTP-сервер на хосте и порте, указанных в конфигурационных переменных API_HOST и API_PORT
2. THE API_Server SHALL инициализировать RAGChain с теми же компонентами, что использует Telegram-бот (Retriever, LLM, embeddings, vector store)
3. WHEN флаг `--api` комбинируется с другими флагами действий (кроме `--gpu`), THE CLI SHALL сообщить об ошибке и отказаться запускаться
4. WHEN API_Server получает SIGINT или SIGTERM, THE API_Server SHALL завершить работу корректно (graceful shutdown)

### Требование 4: Управление процессами

**User Story:** Как разработчик, я хочу, чтобы API-сервер и Telegram-бот работали как отдельные процессы с отслеживанием PID, чтобы управлять их жизненным циклом независимо.

#### Критерии приёмки

1. WHEN API_Server запускается, THE API_Server SHALL записать свой идентификатор процесса в файл `api.pid` в корневой директории проекта
2. WHEN API_Server завершает работу, THE API_Server SHALL удалить файл `api.pid`
3. WHEN Telegram-бот запускается, THE Telegram-бот SHALL записать свой идентификатор процесса в файл `bot.pid` в корневой директории проекта
4. WHEN Telegram-бот завершает работу, THE Telegram-бот SHALL удалить файл `bot.pid`
5. THE API_Server и Telegram-бот SHALL использовать общий файл логов и единую конфигурацию логирования

### Требование 5: Обработка ошибок

**User Story:** Как Client, я хочу получать информативные ответы об ошибках, чтобы понимать и устранять проблемы.

#### Критерии приёмки

1. IF RAGChain выбрасывает VectorStoreError при обработке, THEN THE API_Server SHALL вернуть JSON-ответ об ошибке со статусом 502 и сообщением об ошибке сервиса поиска
2. IF RAGChain выбрасывает LLMError при обработке, THEN THE API_Server SHALL вернуть JSON-ответ об ошибке со статусом 502 и сообщением об ошибке сервиса генерации
3. IF непредвиденное исключение возникает при обработке запроса, THEN THE API_Server SHALL вернуть JSON-ответ об ошибке со статусом 500 и общим сообщением без раскрытия внутренних деталей
4. THE API_Server SHALL логировать все ошибки с полным traceback, используя конфигурацию логирования проекта

### Требование 6: Формат ответов и архитектура

**User Story:** Как Client, я хочу единообразный формат JSON-ответов, а как разработчик — расширяемую структуру маршрутов для будущих эндпоинтов.

#### Критерии приёмки

1. THE API_Server SHALL возвращать все ответы с `Content-Type: application/json`
2. WHEN обработка успешна, THE API_Server SHALL вернуть ответ, сериализованный через Pydantic-модель QueryResponse
3. WHEN происходит ошибка, THE API_Server SHALL вернуть JSON-объект с полем `detail`, содержащим человекочитаемое описание ошибки
4. THE API_Server SHALL организовать маршруты с помощью FastAPI APIRouter для поддержки добавления новых эндпоинтов в будущем
5. THE API_Server SHALL обрабатывать запросы асинхронно с использованием паттерна async/await
6. THE API_Server SHALL выделить бизнес-логику из обработчиков маршрутов в отдельный сервисный модуль (service layer), сохраняя обработчики маршрутов тонкими
